# 测试用例生成（多智能体流水线）

从知识目录生成测试用例，难点从来不是"写够条数"，而是三件事同时成立：**每条用例都能指回需求里的哪句话、每条用例只判一件事、所有用例合起来既没有重复也没有漏**。这三件事里任何一件失守，用例集就会变成一份没人敢用的清单——评审时挑不出错，回归时挡不住缺陷。

所以这套流程不直接产出用例，而是逐级放大：功能点 → 测试场景 → 测试点 → 测试用例。每一级都落盘成可复查的 YAML。理由很实际：**判断"这个功能点切得对不对"比判断"这 40 条用例写得对不对"便宜得多**。级切错了，后面全歪；及早发现，改一行清单比重写一整个套件省事。

多智能体是为了解决另一个问题：一次读完整个知识库再统一分析，读到第 5 个文件时前 4 个的细节已经被挤出上下文了。扇出让每个 agent 只读自己那一片知识，判断更准，也更快。代价是各自为政，所以每一级都必须有合并归一，ID 规则由脚本强约束，不能靠 agent 自觉。

## 输入与输出

**输入**：一个包含知识的目录（如 `wiki/`、`docs/`、`raw/`）。目录里可能是多篇 Markdown、也可能有 PDF/txt；先看有没有 `index.md` 或 README 做导航。目录可以嵌套（`wiki/loyalty/*.md`），扇出前先列出全部知识文件。

**产出语言跟随知识原文**：中文知识出中文用例，英文知识出英文用例。但字段名始终用 `references/yaml-schema.md` 里的英文键——那是脚本和工具链依赖的部分，翻译了就会校验失败。

**输出**：`testcases/<topic>/` 下的一套文件。

| 文件 | 内容 |
| --- | --- |
| `01-functional-points.yaml` | 功能点清单（一级放大） |
| `02-scenarios.yaml` | 测试场景清单（二级） |
| `03-test-points.yaml` | 测试点清单，含证据与设计方法适用性（三级） |
| `testcases.yaml` | 最终用例集（四级，含全部字段） |
| `coverage-report.md` | 覆盖度、方法矩阵、等级分布、待确认清单、冗余/遗漏审查结论 |
| `.shards/` | 各 agent 的原始分片，保留用于追溯和重跑 |

`testcases.yaml` 是交付物，其余四份是过程证据。交付时不要只给最终文件——评审者需要能顺着 ID 往回查。

## 五级分析，三轮扇出

分析仍然是五级——功能点、场景、测试点、用例、合并审查。但**扇出只有三轮**，理由很实际：前三级的推导共享同一份文档上下文。拆成三次扇出后，第二轮的 agent 要重读第一级产物，第三轮再重读第二级，每次都在重建同样的理解，既慢又容易漂。所以一个 agent 读一篇文档，连续推导出它的功能点、场景、测试点。

| 轮次 | 扇出单位 | 产出 | 典型 agent 数 |
| --- | --- | --- | --- |
| A | 知识文件 | 该文件的功能点 + 场景 + 测试点三级分片 | 文件数（3–10） |
| B | 功能点批次 | 测试用例分片 | 4–8 |
| C（可选） | 用例分片 | 冗余与遗漏审查意见 | 0–3，用例超 80 条才开 |

### 第 1 级 — 功能点分析

按**业务对象/规则簇**切功能点，不按页面、不按菜单、不按代码模块。检验标准很朴素：产品经理会不会说"这是一个东西"。一篇 wiki 通常切出 3–8 个功能点；切出 30 个说明你在按页面元素切，切出 1 个说明你在按模块切。

每个功能点必须带 `source_ref`（文件路径 + 章节标题）。找不到出处说明它是你脑补的。

### 第 2 级 — 测试场景分析

对每个功能点列场景，回答"在什么条件下验什么"。默认按下述关注面过一遍，避免只想到 happy path：

正常主链路 · 分支/可选配置 · 边界与阈值 · 异常与非法输入 · 权限与越权 · 状态流转 · 数据一致性 · 并发与竞争 · 安全与防作弊 · 兼容与降级

不是每个功能点都要十类场景。用不上的跳过，但**跳过要知道自己跳过了什么**——所以每个功能点至少要有主链路和一条负向场景，这是底线。

### 第 3 级 — 测试点设计

把一个场景拆成若干**可独立判定真伪**的测试点。测试点的判据是：读完它你立刻能说出"怎么验"。写"验证打卡是否正常"就不是测试点，它永远不会失败。

每个测试点必须带 `evidence.quote`（逐字引用原文）和 `methods`（哪些设计方法适用、哪些不适用及原因）。用户要求的十种方法必须逐一表态——漏掉的方法会被校验脚本点名。不适用要写可反驳的原因，比如 `并发法: 该规则无共享可变状态`，而不是"不适用"三个字。

### 第 4 级 — 测试用例设计

对每个测试点，用**适用的每一种设计方法各生成用例**。一条用例一个主方法、一个目标。

这是整个流程里扇出最大的一级，也是最容易失控的一级。三条约束压住它：

1. **一条用例只判一件事**。测试点里有两个独立判定点，就拆成两条用例。失败时定位不到原因、修复后无法界定回归范围的用例，在回归里长期空转。
2. **数据驱动场景合成一条**。同一动作、不同输入值，写成一条用例的多个数据行，不要拆成五条几乎一样的用例。
3. **证据逐字**。`source_context.quote` 直接抄原文，不改写、不拼接、不加解释。改写过的引用在脚本回扫时必定落空，也说明这条用例的预期结果是推的而不是读的。

### 第 5 级 — 合并审查

前几级各自为政的后果，到这里必须收口。四件事按顺序做：

1. **机械合并**：脚本按 ID 排序合并分片，检出重复 ID。
2. **语义去重**：找"换了个说法但验的是同一件事"的用例。机械脚本只能抓字面重复，语义重复必须靠读。
3. **遗漏审查**：反查覆盖链——每个测试点是否至少有一条用例、每个功能点是否正反成对、每个标为适用的设计方法是否真的产出了用例。
4. **归一与定稿**：合并去重结果，重跑校验脚本，直到硬失败清零。

`references/quality-gates.md` 是这一步的逐条清单。

## 合并与校验：编排者自己做

合并和校验不要各开一个 agent——那是把流水线从十轮拖到二十轮的最快方式。编排者自己用 bash 跑三个脚本就够了：

```bash
python3 <skill-dir>/scripts/merge_shards.py --stage cases \
    --shard-dir testcases/<topic>/.shards/cases --out testcases/<topic>/testcases.yaml \
    --topic <topic> --title "<标题>"
python3 <skill-dir>/scripts/validate_cases.py --topic-dir testcases/<topic> \
    --corpus wiki/<topic> --abbr <ABBR>
python3 <skill-dir>/scripts/render_report.py --topic-dir testcases/<topic> \
    --out testcases/<topic>/coverage-report.md
```

只有当脚本报出重复 ID 或语义重复时，才值得开一个 agent 做语义归一。脚本能确定性完成的事，交给脚本。

## 多智能体编排

用 `workflow` 工具按三轮编排，脚本模板见 `references/multi-agent-playbook.md`（含扇出、失败重试、批处理，以及没有 `workflow` 时的串行降级）。

四条经验规则：

- **总 agent 数控制在 12 个以内，每轮并行 3–8 个**。扇出太细，每个 agent 都要重读 schema 和上游文件，固定开销会吃掉并行收益，总耗时反而更长。功能点有 40 个，不是开 40 个 agent，是分成 6–8 批。
- **agent 之间传路径，不传内容**。每个 agent 把结果写成自己的 shard，返回 `{files, counts}`；下一轮 agent 直接读上一轮合并后的文件。把整份 YAML 塞进 prompt 会让上下文迅速膨胀。
- **分片失败要补跑，不要静默吞掉**。`agent()` 失败返回 `null` 而不是抛异常，用 `.filter(Boolean)` 过滤后对缺失分片补跑一次。少一个分片意味着漏掉一块知识，而后续阶段看起来都正常。
- **中途断了就续跑，不要重来**。每轮落盘后 `01/02/03/testcases.yaml` 就是续跑点。开工先 `ls` 目标目录，已有产物就从最高完成级别继续。轮次 B 分两半发、跑完一半先合并落盘——最长的那一段断掉时，磁盘上往往已经有一个能交付的用例集。

编排者自己的预算是有限资源。发现自己已经发了十几轮 `agent()`，就该收口：先把用例集和报告落盘，审查留到下一轮。**能交付的八成，好过跑到一半断掉的九成。**

预算、失败补跑、断点续跑的硬阈值与判定标准见 `references/loop-governance.md`；阈值以 `governance/policy.yaml` 为准，两者冲突时按 policy 执行。

没有 `workflow` 工具时（例如某些受限环境），**降级为串行**：按同样三轮顺序，在单一上下文里逐级完成并落盘同样的文件。质量要求不降，只是慢。不要因为不能并行就跳过中间产物——那等于放弃了可追溯性。

## 数据模型

字段全表、枚举词表和完整范例见 `references/yaml-schema.md`。最小必填字段：

| 字段 | 含义 | 要点 |
| --- | --- | --- |
| `id` | 用例 ID | `TC-<ABBR>-<FF><SS>`，FF 是功能点序号，SS 是序号 |
| `fp_id` / `scenario_id` / `point_id` | 四级追溯链 | 三级必须互相对得上，脚本校验 |
| `functional_point` | 用例所属功能点 | 人读文本，与 `fp_id` 一致 |
| `scenario` | 测试场景 | 在什么条件下，不含动作、不含预期 |
| `test_point` | 测试点 | 要判定什么，可判定真伪 |
| `title` | 测试用例 | 做什么动作，一句话 |
| `design_method` | 设计方法 | 单个主方法，见词表 |
| `tags` | 关键标签 | 1–3 个，见词表 |
| `severity` | 严重等级 | S1–S5，五档 |
| `preconditions` | 前置条件 | 环境与数据，不写动作 |
| `steps` | 测试步骤 | 2–6 步，每步一个动作，不嵌预期 |
| `expected` | 测试结果（预期） | 可判定；`actual` 可选，执行后回填 |
| `source_context` | 原始文档上下文 | 逐字 `quote` + `path` + `section` |

`scenario` / `test_point` / `title` 是三个不同粒度，通读成「在**场景**下，验证**测试点**，操作为**用例**」。读不通就是字段混了。这个检查很灵敏：三者混用的用例，几乎总是接着出现不可判定的预期结果。

## 五条硬原则

1. **证据逐字**。`source_context.quote` 必须在知识原文里命中（脚本回扫，norm 掉空白与全半角）。命中不了，说明这条用例是编的，删掉或改。
2. **不臆造行为**。知识没写的地方不编预期。标 `status: pending_confirmation`，预期写"待确认：<要确认的具体问题>"，并登记进 `open_items`。这是整套产出可信度的来源——读用例的人能分清哪些是需求承诺、哪些是待补的空白。
3. **单一目标**。一条用例只判一件事。
4. **可追溯**。TC → TP → SC → FP 四级链不能断。断链的用例等于没有需求依据，评审时无法判断它该不该存在。
5. **正反成对**。每个功能点至少一条正向主链路 + 一条异常/边界。100 条正向用例不如 30 条正反成对的用例。

## 设计方法

12 种方法、各自触发条件与写法要点见 `references/design-methods.md`。核心是**逐点过筛**而不是平均用力：对一个测试点，通常 2–4 种方法适用，其余要在 `methods.skipped` 里写明不适用的原因。

用户要求的十种方法（边界值法、等价类划分、错误推测法、穷举法、逆向场景法、因果图法、场景法、异常法、并发法、安全性法）**必须对每个测试点逐一表态**——要么进 `applicable`，要么进 `skipped` 并给原因。漏掉的方法会被校验脚本点名。这条不是形式主义：绝大多数"只写了等价类划分"的用例集，问题不是想不出别的方法，而是根本没逐点想过边界、并发、越权在哪。全写"等价类划分"等于没做方法分析。

| 方法 | 什么时候用 |
| --- | --- |
| 边界值法 | 有数值阈值：分钟数、距离、人数上限、时间窗 |
| 等价类划分 | 输入可切互斥类：范围内/外、某部门/某成员 |
| 错误推测法 | 越权、绕过入口、非常规路径、文档留白处 |
| 穷举法 | 组合空间小且必须全覆盖（枚举开关的有限组合） |
| 逆向场景法 | 从"怎样才能让它出错"倒推，专攻主链路的反方向 |
| 因果图法 | 多条件与结果的因果缠绕，判定表表达不下时 |
| 场景法 | 按业务主线串联配置与操作，验端到端可用 |
| 异常法 | 非法输入、缺失依赖、超时、断网、脏数据 |
| 并发法 | 同一数据被多方同时读写、重复提交、幂等 |
| 安全性法 | 越权访问、防作弊、防篡改、数据泄露 |
| 判定表法 | 多个开关/条件组合决定结果，可穷举成表 |
| 状态迁移法 | 有明确状态机：待审批 → 通过 → 校准 |

## 严重等级（5 档）

| 等级 | 名称 | 判定标准 |
| --- | --- | --- |
| S1 | 致命 | 核心业务不可用、数据错误、权限越权，直接影响对外结果 |
| S2 | 严重 | 主要功能失败或结果与规则不一致，用户无法完成关键操作 |
| S3 | 一般 | 次要功能异常，或有可用替代路径，影响范围有限 |
| S4 | 轻微 | 提示、展示、体验类问题，不影响业务结果 |
| S5 | 建议 | 优化建议或边界补充，非缺陷 |

定级看**后果**不看实现难度，也不看用例方向。三个问句按顺序问，第一个"是"就停：

1. 失败后用户能否完成核心任务？数据会不会错？权限会不会穿？——任一为是 → S1
2. 主要功能会不会整个失效，或结果与规则不符？——是 → S2
3. 有没有替代路径？——有 → S3；只是展示/提示 → S4；只是建议 → S5

**定级看断言内容**：一条正向用例如果断言金额、余额、权限这类数，算错就是 S1；一条异常用例如果只断言提示文案，反而是 S4。"正向=S2、异常=S1"是最常见的定级错误，它会把最致命的算错金额用例降级。

**分布自查**：健康套件的 S1 一般占 10%–25%，超过 30% 校验脚本会告警。但这是复核触发器，不是配额——资金结算、权限管控这类需求核心链路本来就密，S1 占四成是合理的。为了过阈值把"钱算错"降成 S2，比 S1 通胀更糟。

## 校验输出怎么读

`validate_cases.py` 分两类输出：

- **硬失败（非零退出，必须修）**：缺字段、ID 重复或不合规则、四级追溯链断裂、枚举越界、引用原文命中失败、用例数为零。
- **告警（需要判断，不阻断）**：语义疑似重复、测试点无对应用例、功能点缺正向或缺负向、某适用方法未产出用例、核心方法未过筛、S1 占比过高、预期结果含"正常/正确/友好"这类不可判定词、步骤过少、`pending_confirmation` 未登记 `open_items`。

告警不是噪音，是交付前最该复看的地方。**硬失败清零就交付是不合格的**，告警也要逐条读。`references/quality-gates.md` 给了每类告警的处理原则。

## 交付时给出什么

1. `testcases/<topic>/testcases.yaml` —— 用例集主体。文件名格式：testcase+时间戳.yaml
2. `coverage-report.md` —— 覆盖度结论（各级数量、TP 覆盖率、方法矩阵、等级分布）、冗余与遗漏审查结论、待确认清单。
3. 一段话结论：这套用例覆盖了哪几个功能面、覆盖到什么程度、哪几处知识没写清所以只能标待确认。

待确认清单是这套方法的诚实标注，不要为了交付好看而省掉。

## 反模式

- **跳过中间级直接写用例**：结果是遗漏功能点、重复用例、无法追溯，而且这三样在评审时都看不出来。
- **用例写成需求复述**："测试打卡功能是否正常"——没有判定点，永远不会失败。
- **预期结果不可判定**："提示信息友好""显示正确"——谁来判定友好？
- **编造知识里没有的行为**：需求没写超时时间，却断言"30 秒后锁定"。这类断言一旦被发现，整套用例的可信度都会被打折。
- **一条用例塞多个判定点**：失败定位不到原因，回归无法界定范围。
- **把并行当目标**：为了开满 agent 把一篇文档按章节拆碎，上下文丢光，产出还不如串行。
- **覆盖度按用例数算**：用例数是工作量指标，不是覆盖度指标。分母应该是测试点。
