# 质量门禁与审查清单

交付前的最后一道关。分两段：脚本能判的（机械门禁）和只有读才能判的（语义审查）。**两段都过才算完成**，脚本全绿只说明格式没坏。

## 一、机械门禁

```bash
python3 <skill-dir>/scripts/validate_cases.py --topic-dir testcases/<topic> \
    --corpus wiki/<topic> --abbr <ABBR>
```

非零退出即为不合格。硬失败逐类含义与修法：

| 硬失败 | 它实际在说什么 | 修法 |
| --- | --- | --- |
| `missing_field` | 必填字段空着 | 补；补不出来说明这条用例没想清楚 |
| `bad_id_pattern` | ID 不合规则 | 按 `TC-<ABBR>-<FF><SS>` 改 |
| `duplicate_id` | 两个 agent 撞号 | 按号段重编，并检查下游引用 |
| `broken_chain` | 用例的 point/scenario/fp 对不上 | 通常上游重编号后没同步，批量修 |
| `bad_enum` | 方法/标签/等级越界 | 从词表取，不要自创 |
| `ungrounded_quote` | 引用在原文里找不到 | **改引用或删用例**，不要改原文去迁就用例 |
| `no_cases` | 一条用例都没有 | 检查是不是扇出分片全失败了 |

`ungrounded_quote` 要保持硬失败。它是唯一能机械发现"编造需求"的检查，一旦降成告警，整套产出就失去了可信度锚点。

告警要逐条读，不要求清零。每类告警的处理原则：

| 告警 | 处理 |
| --- | --- |
| `tp_without_cases` | 必须处理：测试点没被验，等于漏测 |
| `fp_missing_negative` | 必须处理：缺负向，缺陷会从反方向漏出 |
| `method_uncovered` | 判断：该测试点是否真的需要这个方法的用例 |
| `methods_incomplete` | 必须处理：有核心方法没被过筛，说明该测试点的设计思考不完整 |
| `near_duplicate` | 判断：是数据驱动合并后的正常近似，还是真重复 |
| `vague_expected` | 必须处理：不可判定的预期等于没写 |
| `s1_ratio_high` | 判断：资金/权限类需求可豁免，其余逐条降级 |
| `pending_not_registered` | 必须处理：待确认项没登记，交付后无人跟进 |
| `scenario_equals_point` | 必须处理：三个一句话字段混了 |

## 二、语义审查

机械门禁查不出"两条用例换个说法验同一件事"，也查不出"两个功能点之间漏了一整块"。这段只能读，按下面四轮做，每轮只看一件事——混着看会漏。

### 第 1 轮：冗余

**判据**：两条用例的「前置条件 + 动作 + 判定对象」三者实质相同，只是措辞不同 → 重复。

合并方式不是删掉一条，而是保留信息更全的那条，把另一条里独有的预期并入。删除前确认它没有覆盖任何别的测试点。

数据驱动合并后的近似不算重复：同一动作五个输入值合成一条用例的五个数据行，是正确做法，不要拆散。

### 第 2 轮：遗漏

按覆盖链反查，四级都要查到：

- 每个功能点至少 1 个场景；每个场景至少 1 个测试点；每个测试点至少 1 条用例。
- 每个功能点至少 1 条 `正向` 和 1 条 `异常`/`边界`/`逆向` 类用例。
- 测试点里 `methods.applicable` 标了的方法，是否都有对应用例。
- 知识里带"必须/只能/不得/超过/默认"的句子，是否都落成了测试点或 `pending_confirmation`。

最后一条最关键：**回去读原文找限定词**，比在读用例里找缺口有效得多。限定词是漏测的高发区。

### 第 3 轮：定级

逐条问"这条失败后会发生什么"，按 S1→S5 顺序问到第一个"是"就停。重点复查两类：

- 断言涉及金额、余额、权限、库存、考勤结果的，出错就是 S1。
- 只断言提示文案的异常用例，通常 S3–S4，不要因为它是异常场景就给 S1。

看全表分布：S1 超过 30% 时，逐条重新问一遍第一句。

### 第 4 轮：可执行性

挑 10 条用例，假设自己是执行人，问三个问题：

1. 前置条件够不够让我搭出这个环境？缺数据、缺账号、缺已完成配置，就无法复现。
2. 步骤能不能照做？出现"配置好相关参数""按需设置"这类话就是没法执行。
3. 预期结果我能不能用眼睛或脚本判定？"显示正确""体验流畅"不可判定。

抽中的 10 条里超过 2 条不合格，全表按同样问题过一遍。

## 三、审查 agent 的指令要点

审查最容易跑偏成"顺手重写"。指令里必须限定输出形态：**只报问题，给出可定位的改法，不重写文件**。

```
你是「用例审查」agent，负责 ${module} 模块的 ${n} 条用例（${first}–${last}）。

只做四件事，每件都要给具体用例 ID 和具体的改法：
1. 冗余：前置+动作+判定对象实质相同的用例组，指出保留哪条、并入什么。
2. 遗漏：对照 ${知识文件} 的限定词（必须/只能/不得/超过/默认），指出缺的测试点。
3. 定级：只报你认为定级错误的，写明失败后果和应改等级。
4. 可执行性：前置/步骤/预期不可执行的，指出具体哪一项。

不要改写用例正文，不要输出整份文件。用列表输出，每项一行：问题类型 | 用例ID | 问题 | 建议改法。
没有问题就明确说"无"。
```

审查 agent 拿到的用例分片要带完整字段（前置、步骤、预期都在），否则它判不了可执行性。

## 四、交付前最后一次自查

- [ ] `validate_cases.py` 硬失败为零
- [ ] 四类"必须处理"的告警已处理
- [ ] 四级追溯链抽检 5 条，ID 全部对得上
- [ ] 每个功能点都有正向和负向用例
- [ ] `open_items` 与 `pending_confirmation` 用例一一对应
- [ ] 覆盖度报告里的数字与 YAML 实际条数一致
- [ ] 抽 10 条按第 4 轮标准自查可执行性
- [ ] 报告里写明了本次没覆盖什么、为什么

最后一项常被跳过。一份明说"这三块因为知识没写清所以只标了待确认"的用例集，比一份假装全都覆盖了的用例集有用得多。
