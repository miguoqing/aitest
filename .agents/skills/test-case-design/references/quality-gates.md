# 质量门槛

交付前逐条过。前四条是硬门槛，任何一条不过就不要交付；后四条是质量线，不过要说明原因。

## G1 引用可回扫

每条用例的 `context.quote` 必须在需求来源里逐字存在。跑：

```bash
python3 scripts/verify_grounding.py --input cases.json --corpus wiki/<topic> --corpus raw/<topic>
```

回扫会先归一化空白，所以"MAC 地址"与"MAC地址"视为同一句；但**不允许**同义改写、语序调整、拼接两句、截断到半句再补句号。原则很简单：引用是用来被查证的，不是用来读起来顺的。

拼接两句最容易翻车：原文 A 句 + B 句中间还隔着一句 C，你把 A+B 连起来写，读者以为原文如此，实际是加工过的。要么只引一句，要么引连续的整段。

## G2 未定义行为不臆造

文档没写的行为，预期结果里写「待确认」，并按以下格式登记：

- 在 `open_items` 里加一条：待确认项名称、关联用例、文档缺口说明（具体到"哪句话没写清"）。
- 在用例预期结果里说明"待确认：文档仅说明 X，未定义 Y；确认前不作为缺陷判定依据"。

这条门槛保护的是整个交付物的可信度。混入一条编造的断言，评审人就会开始怀疑全部用例。

## G3 判定点全覆盖

`points` 里的每个判定点，要么至少有一条用例 `covers` 它，要么状态标为 `部分覆盖` / `未覆盖（待确认）` 并说明原因。

覆盖度分母用判定点数，不用用例数。用例数只反映工作量。

## G4 预期结果可判定

自检问句：**"如果实现错了，这条预期会不会仍然通过？"** 会通过，就重写。

常见不可判定的写法：

- "显示正确""功能正常""符合预期" —— 同义反复
- "提示信息友好" —— 主观
- "性能良好" —— 没有阈值
- "数据一致" —— 没说哪两份数据、比哪些字段

## G5 正反成对

每个功能点检查：有没有一条"该拒绝的场景被拒绝了"的用例？只有正向用例的套件，等于只验了一半。

典型的反例对子：勾选了拍照要求 → 不拍照应被拒；未勾选 → 不拍照应通过。只写后者，缺陷从前者漏出。

## G6 步骤可复现

把用例交给没参与设计的人，他能照着跑完并得到唯一结论吗？

判据：前置条件里有环境与数据、步骤里有具体入口路径、预期里有具体可见结果。缺任何一项，执行时就会变成"我这里好像没问题"。

## G7 一条用例一个判定点

一条用例挂多个判定点，失败时定位不到原因，修复后也无法确认回归范围。数据驱动的同构场景合成一条（步骤里写用例 A/B），异构的判定点必须拆开。

## G8 命名与编号一致

- ID 唯一且递增，删除用例后不复用编号（否则历史缺陷单对不上）。
- 功能点名与 `functional_points` 的 key 一致，不要文档里一处叫"打卡方式"、另一处叫"打卡类型"。
- 测试点、测试用例、预期结果三者用同一套术语，与需求原文的用词一致（需求叫"补卡申请"，就不要写成"补打卡"）。

## G9 等级分布自查

交付前看一眼严重等级分布：

- S1 占比超过 30% —— 先复核：逐条重问"失败后用户还能不能完成核心任务"。资金/权限密度极高的需求可豁免，但要在报告里说明一句。
- S1 占比为 0 —— 要么需求里没有核心链路（少见），要么你在回避真正的风险路径。
- 全部集中在 S2 —— 通常是没有区分"整个功能挂了"和"某个分支错了"。

参考区间：S1 10%–25%、S2 30%–50%、S3 20%–35%，S4/S5 合计不超过 15%。

## G10 待确认双写

预期结果里写了「待确认」的用例，必须在 `open_items` 里有一条对应登记；反之 `open_items` 的 `case_id` 必须存在。

只写一处等于没写：用例里标了待确认但缺口清单没有，评审时会被当成"需求遗漏"；缺口清单里挂了但用例没标，执行人会把待确认当成明确的验收标准。`verify_grounding.py` 会对此告警。
