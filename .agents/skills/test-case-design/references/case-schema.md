# 用例规范

## 字段最小集

| 字段 | 必填 | 说明 | 常见错误 |
| --- | --- | --- | --- |
| 用例ID | 是 | `TC-<模块缩写>-NNN`，三位递增，不复用 | 一个模块出现两套编号体系 |
| 功能点 | 是 | 对应 `functional_points` 的 key | 把页面名当功能点 |
| 测试场景 | 是 | 在什么条件下（不含动作、不含预期） | 与测试点写重、把步骤塞进场景 |
| 测试点 | 是 | 要判定什么，可判定真伪；可比判定点更具体 | 写成"是否正常"、照抄判定点编号文本 |
| 测试用例 | 是 | 做什么动作，一句话 | 写成场景复述 |
| 设计方法 | 是 | 见下方词表，取主方法 | 每条都写"等价类划分" |
| 关键标签 | 是 | 见下方词表，2 个以内 | 标签爆炸（一条挂 5 个） |
| 严重等级 | 是 | S1–S5 | 按实现难度定级 |
| 前置条件 | 是 | 环境、数据、已完成的配置；不写动作 | 把第一步写进前置 |
| 测试步骤 | 是 | 3–6 步，每步一个动作，不嵌预期 | 一步里塞三个操作 |
| 预期结果 | 是 | 可判定的具体状态；列表 | "显示正确""功能正常" |
| 原始文档上下文 | 是 | 需求原文逐字引用 + 来源文件 | 转述、拼接、加"我认为" |
| 依据文档 | 是 | 引用所在文件（wiki 或 raw） | 指到目录而不是文件 |

## 设计方法词表

选最贴合的主方法，不要堆砌。

| 方法 | 什么时候用 |
| --- | --- |
| 场景法 | 按业务主线串联配置与操作，验端到端可用 |
| 判定表 | 多个开关/条件组合决定结果（或/且关系、开关矩阵） |
| 边界值分析 | 有数值阈值：分钟数、距离、人数上限、时间窗 |
| 等价类划分 | 输入可分互斥类：范围内/外、部门/成员、状态分类 |
| 错误推测 | 越权、绕过入口、非常规路径、文档留白处 |
| 状态迁移 | 有明确状态机：待审批→通过→校准 |
| 流程分析 | 多步链路：导入导出、权限分配、系统集成 |
| 矩阵分析 | 同一数据在多套配置下的横向对比 |
| 因果图 | 多条件因果关系复杂，判定表表达不下时 |

## 标签词表

| 标签 | 含义 |
| --- | --- |
| 正向 | 正常路径，需求承诺的主链路 |
| 异常 | 负向路径，应被拒绝或不应发生 |
| 边界 | 阈值、上下限、恰好命中 |
| 权限 | 角色、范围、越权 |
| 数据准确性 | 结果数值/状态算得对不对 |
| 数据一致性 | 多处数据是否口径一致（导出 vs 页面、API vs 后台） |
| 冒烟 | 每次提测必跑 |
| 安全 | 防作弊、防截图、防改包 |
| 集成 | 跨系统对接 |
| 导出 | 文件导出与格式 |
| 回归 | 已修复缺陷的守护用例 |
| 待确认 | 文档未定义，预期结果待产品结论 |
| 建议 | 非缺陷，体验或规范建议 |

## 严重等级

| 等级 | 名称 | 判定标准 | 典型场景 |
| --- | --- | --- | --- |
| S1 | 致命 | 核心业务不可用、数据错误、权限越权 | 考勤数据算错、范围外管理员能改规则 |
| S2 | 严重 | 主要功能失败或结果与规则不一致 | 开关勾了不生效、审批通过后状态不变 |
| S3 | 一般 | 次要功能异常，或有可用替代路径 | 提醒时机偏差、筛选漏一种组合 |
| S4 | 轻微 | 提示、展示、体验类 | 文案措辞、时间格式 |
| S5 | 建议 | 优化建议或边界补充 | 下拉项排序、默认值选择 |

定级看后果：修不好会造成数据错、钱算错、权限穿的，就是 S1。

`points[].status` 取值：`覆盖`、`部分覆盖`、`覆盖（含待确认分支）`、`未覆盖（待确认）`。

`open_items[].case_id` 可以写多个用例，用 `、` 分隔（如 `TC-ATT-003、TC-ATT-007`），校验脚本会逐个核对。

**状态不能靠声明**：判定点声明「覆盖」但没有任何用例的 `covers` 引用它时，校验脚本会把它降级为未覆盖并告警。覆盖度只认真实引用，不认自我声明。

## 三个一句话字段的分工

| 字段 | 回答的问题 | 打卡示例 |
| --- | --- | --- |
| 测试场景 | 在什么条件下 | 手机打卡时定位处于有效范围内 |
| 测试点 | 要判定什么 | 定位命中范围即打卡成功并记录 |
| 测试用例 | 做什么动作 | 员工在范围内打卡，检查记录归属 |

通读成「在**场景**下，验证**测试点**，操作为**用例**」，读不通就是三者混了。

测试点允许比判定点更具体（判定点是一句需求承诺，测试点是它在这条用例上的可验形式），但不要把判定点编号的原文照抄一遍——照抄等于没写测试点。

## 写作对照

| 差 | 好 | 为什么 |
| --- | --- | --- |
| 验证打卡是否正常 | 定位在有效范围内打卡成功，记录归属该员工当日考勤 | 前者永远不会失败 |
| 提示信息友好 | 提示「不在打卡范围内」，且不生成打卡记录 | "友好"不可判定 |
| 测试超时锁定 | （文档未定义）待确认：超时后是否锁定 | 需求没写就不能断言 |
| 前置：打开页面，选择规则，点击保存 | 前置：规则已保存且绑定测试部门；步骤：员工打卡 | 前置写成了步骤 |
