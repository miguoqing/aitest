# 测试用例设计

把需求文档变成一套能执行、能回扫、能统计的测试用例。

核心不是"多写几条用例"，而是让每条用例都能回答三个问题：**它来自需求里的哪句话？它判定的是什么？失败说明什么坏了？** 三者里只要有一项答不上来，这条用例就是噪音，会在回归里长期空转。

这套流程的产出物是两份文件：一份人读的 Markdown 用例文档，一份进测试管理工具的 Excel。两者由同一份 `cases.json` 渲染，改数据即可重生成，不会漂移。

## 四条硬原则

1. **证据优先**：每条用例必须附一段需求原文引用（verbatim），并且能被 `scripts/verify_grounding.py` 机械回扫命中。引用可以是需求文档里的原句，也可以是 wiki 编译稿里的原句——但必须逐字存在。
2. **不臆造行为**：文档没写的地方不编预期结果。标「待确认」，登记进缺口清单，明确写"确认前不作为缺陷判定依据"。这是这套流程可信度的来源：读用例的人知道哪些是需求承诺，哪些是待补的空白。
3. **判定点驱动**：先抽需求里"能被判定真伪"的句子（含数字、开关、状态、权限边界），登记成带编号的判定点，再为判定点设计用例。这样覆盖度是可计算的，不是拍脑袋的百分比。
4. **正反成对**：每个功能点至少一条正向主链路 + 一条异常/边界。只有正向用例的套件，缺陷会从反方向全部漏出。

## 工作流

### 步骤 1 — 定位需求来源

优先顺序：

1. 项目里有 `wiki/<topic>/` 编译稿 → 读它。wiki 已经做过一次事实压缩，噪音比原始 PRD 少，且每条事实都有 raw 出处。
2. 只有 `raw/` 原始材料 → 直接读原始材料。
3. 都没有 → 让用户提供文件或粘贴内容。**不要凭常识补全需求**。

读的时候同时确认两件事：文档覆盖了哪些模块（用来划功能点），以及文档里哪些句子带"必须/只能/不得/超限/默认"这类限定词（这些就是判定点的矿脉）。

### 步骤 2 — 抽取判定点并编号

把文档里"可被判定真伪"的句子抄成清单，编号 `P1-1`、`P2-3`（前缀是第几篇文档，或第几个功能点）。

判定点的特征是：读完之后你能立刻说出"怎么验它"。典型来源：

- 带数字的约束（100至300米、允许迟到 N 分钟、人数上限）
- 开关型规则（勾选 X 后行为变化）
- 权限边界（只能、不可见、仅范围内）
- 状态流转（审批通过后 → 校准为正常）
- 默认值（系统默认所有人可见）

一句写得好的判定点同时也就写好了用例的骨架。判定点清单是后面覆盖度报告的分母，编号 `P*`；后面用例里的「测试点」是它在这一条用例上的具体化说法，两者是同一件事的粗粒度与细粒度，别写成两套概念。

### 步骤 3 — 划分功能点与测试场景

按业务对象切功能点，而不是按页面切。例如打卡模块：规则类型、打卡人员、打卡方式、地点与范围、容差、外出打卡、拍照、补卡、特殊日期、提醒、可见范围、审批校准、权限、导出、API。

每个功能点下面列测试场景（一句话描述"在什么条件下验什么"）。场景是分组的抓手，用例是场景的展开。

### 步骤 4 — 逐条设计用例

字段最小集见 `references/case-schema.md`，包括：用例ID、功能点、测试场景、测试点、测试用例、设计方法、关键标签、严重等级（S1–S5）、前置条件、测试步骤、预期结果、原始文档上下文、依据文档。

写作要点：

- **测试场景 / 测试点 / 测试用例** 是三个不同粒度的一句话，写成一句通读能立刻发现混淆：「在<场景>下，验证<测试点>，操作为<用例>」。
  - 场景：在什么条件下（「手机打卡时定位处于有效范围内」）
  - 测试点：要判定什么（「定位命中范围即打卡成功」）
  - 用例：做什么动作（「员工在范围内打卡，检查记录归属」）
  三者读不通，就是字段没分清。测试点可以比判定点更具体，但不要只是把判定点编号的文本抄一遍。
- **前置条件**写环境与数据，不要写动作。缺了它，别人复现不了。
- **测试步骤** 3–6 步，每步一个动作。步骤里不嵌预期。
- **预期结果**必须可判定：要么是具体状态，要么是具体可见/不可见。禁止"验证功能正常""显示正确"这类同义反复。
- 数据驱动场景（同一动作、不同输入）合成一条用例，步骤里写"用例 A / 用例 B"，不要拆成三条几乎一样的用例。

设计方法与标签的词表在 `references/case-schema.md`，选最贴合的一个主方法，不要每条都写"等价类划分"。

### 步骤 5 — 落地为 cases.json 并渲染

把用例写进 `testcases/cases.json`（结构见 `assets/example-cases.json`），然后（脚本路径相对本技能目录，在项目根目录执行时写成绝对路径）：

```bash
python3 <skill-dir>/scripts/build_cases.py --input testcases/cases.json --out-dir testcases
```

生成 `testcases/<slug>-test-cases.md` 与 `.xlsx`。Excel 含筛选、冻结表头、严重等级配色，以及独立的覆盖度统计页。没有 openpyxl 时会降级输出 CSV，不会失败。

渲染前先把内容写扎实，不要指望模板救内容。

### 步骤 6 — 质检与覆盖度

```bash
python3 <skill-dir>/scripts/verify_grounding.py \
    --input testcases/cases.json \
    --corpus wiki/<topic> --corpus raw/<topic>
```

它做的检查分两类：

- **硬失败（非零退出，必须修）**：引用未在来源中命中、字段缺失、编号重复、等级非法、设计方法不在词表内、covers 指向不存在的判定点。
- **告警（需要判断，不阻断）**：引用疑似跨行拼接、判定点声明了「覆盖」却没有任何用例 covers 它（该判定点不计入覆盖）、标签超过 2 个或不在词表、步骤少于 2 步、预期里写了待确认但 open_items 没登记、S1 占比超过 30%。

告警不是噪音，是评分卡：它标出的地方通常正是交付前最该复看的地方。

覆盖度的口径、状态分类与报告结构见 `references/coverage-report.md`。

### 步骤 7 — 交付

交付时给出三样东西：用例文档（md + xlsx）、覆盖度结论（判定点覆盖率、等级分布、S1 必跑集）、待确认清单。待确认清单是这套方法的诚实标注，不要省。

## 严重等级（5 档）

| 等级 | 名称 | 判定标准 |
| --- | --- | --- |
| S1 | 致命 | 核心业务不可用、数据错误或权限越权，直接影响对外结果 |
| S2 | 严重 | 主要功能失败或结果与规则不一致，用户无法完成关键操作 |
| S3 | 一般 | 次要功能异常或有可用替代路径，影响范围有限 |
| S4 | 轻微 | 提示、展示、体验类问题，不影响业务结果 |
| S5 | 建议 | 优化建议或边界补充，非缺陷 |

定级看**后果**不看实现难度。三个问句按顺序问，第一个"是"就停：

1. 失败后用户能否完成核心任务？数据会不会错？权限会不会穿？——任一为是 → S1
2. 主要功能会不会整个失效，或结果与规则不符？——是 → S2
3. 有没有可用的替代路径？——有 → S3；只是展示/提示 → S4；只是建议 → S5

**分布自查**：健康套件的 S1 一般在 10%–25%。如果你发现自己把一半用例都定了 S1，通常是"业务重要"被当成了"坏了致命"——支付、金额、权限这类领域尤其容易整体上浮。回头逐条问第一句，把"重要但失败后可恢复"的降下来。反过来，如果一条 S1 都没有，说明你没在验真正会出事的路径。

但这条只是**复核触发器，不是配额**。资金结算、清分、权限管控这类需求，核心链路本来就密，S1 占到四成以上是合理的。豁免要满足一个可检验的条件：**逐条问"这条失败后是否必须回滚数据或补账"**，全部为是，才在报告里写一句"本需求核心规则均落在资金/权限上"并保留定级。

模块里只要还混着纯展示、纯提示类用例，比例自然会回落到区间内；如果整体超过 40% 而回滚测试并不成立，那就是通胀，逐条降级。为了过阈值把"钱算错"降成 S2，比 S1 通胀更糟。

**定级看断言内容，不看用例方向**。一条正向用例如果断言的是金额、余额、库存、权限这类数，算错就是 S1；一条异常用例如果只断言提示文案，反而是 S4。新手最容易犯的错是"正向=S2、异常=S1"，那会把最致命的算错金额用例降级。

## 反模式

- **用例写成了需求复述**："测试打卡功能是否正常"——没有判定点，无法失败。
- **预期结果不可判定**："提示信息友好"——谁来判定友好？
- **编造文档没有的行为**：需求没写超时时间，却断言"30 秒后锁定"。这类断言在评审时最伤信任。
- **只覆盖正向**：100 条正向用例不如 30 条正反成对的用例。
- **覆盖度按用例数算**：用例数量是工作量指标，不是覆盖度指标。分母应该是判定点。
- **一条用例塞多个判定点**：失败时定位不到原因，修复后无法确认回归范围。
